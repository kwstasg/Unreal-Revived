OpenXR loading, session creation, eye swapchains and stereo rendering are opt-in.
`-novr` wins over both `-vr` and stored `EnableVR=True`. Camera/aim hooks install
only after the renderer reports a valid pose; their callbacks also check it.
Desktop HUD and input retain their normal branches.

ModernConsole still probes cached pose availability in desktop mode; this does
not start or query OpenXR. The two VR-only RGBA16F textures are now allocated
only when OpenXR rendering is ready, saving about 31.6 MiB at 1920x1080 or
126.6 MiB at 3840x2160 in desktop mode, before allocation overhead. Buffer
readiness detects mode changes so initial desktop allocation can be rebuilt
after OpenXR initializes. Desktop/fallback smoke checks passed; the active
headset allocation transition still needs runtime validation.

## Startup checkbox and shortcuts

The user chose shortcut-based startup, so the Preferences startup checkbox was
removed. Explicit normal `-novr` and VR `-vr` shortcuts select the mode; stored
`EnableVR` remains only a legacy fallback for direct executable launches.
Preferences Restart now queries `D3D12 VRLAUNCHMODE` before changing renderers
and preserves the requested launch mode, including when OpenXR is unavailable.
Interactive restart validation remains pending.

Installer source previously offered only one desktop shortcut without an explicit
mode override. It now has independent normal and VR desktop tasks (VR unchecked),
plus both Start-menu entries. Normal and postinstall launches use `-novr`; VR uses
`-vr`. Development shortcuts use the same explicit mode selection. No release,
tag, installer publication or automatic installation is part of this audit.
The development recovery launcher also passes `-novr` so a copied enabled VR
preference cannot activate the headset during recovery.

## Confirmed defect corrected

`ModernConsole.LaunchUWindow` still called `RESETVRUIANCHOR` even after renderer
mode recentering was removed. This contradicted the documented explicit-only
recenter rule. The automatic call is now removed; the Preferences button remains.
The accepted canvas projection, logical layout, panel size and anchor math are
unchanged. The previous milestone's source review missed this script call.

## Implemented movement step

The native SDL/XInput poll path rotates shaped movement into horizontal headset
yaw, including the difference between pawn body yaw and view yaw. Rotation is
applied after the response curve and in axis-speed units, preserving magnitude.
Forward/back and strafe stay orthogonal; head pitch/roll cannot introduce vertical
movement. The right stick supplies smooth body yaw; its pitch axis is suppressed
in this VR walking/falling path. Head rotation remains separate from body yaw.

Conditions: valid cached VR pose, living first-person pawn, walking/falling,
no alternate view target or free-look modifier. Plain JoyX `aStrafe` and JoyY
`aBaseY` bindings are handled, including axis speeds. Custom compound bindings
and aliases remain untouched. JoyZ/JoyR used for menu navigation are unchanged.
Keyboard/mouse and non-VR stick processing retain their existing behavior.

Swimming/flying, third-person, spectators and custom movement states are not
claimed as completed VR locomotion. Tracking-loss fallback uses existing input.
The user headset-tested and accepted forward/back/strafe while looking 90 degrees
left/right, and right-stick turning while walking. This acceptance does not
extend to the other movement states above.

## Alignment and remaining work

The plan still contained stale claims that preferences/spatial UI did not exist,
that both eyes showed the same frame, and that delayed HUD following was planned.
These have been corrected. The fixed shared UI panel supersedes automatic HUD
following. The Preferences button now requests combined view/UI recenter:
clear software pitch/roll, preserve current horizontal gaze, refresh the seated
tracking reference, and recapture the upright panel. It runs before either eye
is rendered. This combined action awaits headset validation and cannot calibrate
physical headset fit or recover an unknown earlier yaw direction.

Priorities after movement acceptance:

1. Headset validation of lazy VR buffers and combined recenter.
2. Swimming/flying and body-heading semantics, plus tracking-loss transition tests.
3. Head-through-wall fade and suppression of incompatible bob/forced camera effects.
4. Interactive validation of Preferences Restart in both shortcut modes.
5. Gaze aim compatibility across weapons/custom pawns and multiplayer. Existing
   AdjustAim/AdjustToss hooks do not prove all weapon fire paths use gaze; 227
   client-side ScriptHook support also depends on server permissions.
6. Selectable desktop mirror, Meta/SteamVR coverage, and installed-runtime tests.
